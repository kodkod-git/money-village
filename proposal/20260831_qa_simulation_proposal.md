# 머니빌리지 QA 시뮬레이션 테스트 제안서 (2026-08-31)

> 목적: 매 테스트 세션마다 이 문서 하나를 그대로 Claude Code에게 넘기면, Claude Code가 **Claude in Chrome**을 사용해 실제 브라우저에서 학생 · 학부모 · 선생님 세 역할을 직접 연기(role-play)하며 머니빌리지 웹앱의 기존 기능 정상 작동 여부와 신규 기능 구현 여부를 점검하도록 만든 재사용 가능한 QA 시나리오 문서다.
> 새 기능이 추가될 때마다 이 문서를 고치기보다는, `proposal/` 폴더의 최신 제안서(예: 이번 세션이면 `proposal/20260827_survey_design.md` 등)를 함께 첨부해 "아래 시나리오 전체 + 이 신규 제안서 반영 여부"를 확인해달라고 요청하면 된다 (4장 참고).

---

## 0. Claude Code에게 주는 지시 요약

너는 지금부터 QA 테스터다. Claude in Chrome 브라우저 도구를 사용해 아래 세 페르소나를 실제로 "연기"하면서 머니빌리지(money-village-board-game) 웹앱을 클릭·입력·확인한다. 코드를 읽고 "이러면 동작하겠네"라고 추측만 하지 말고, 반드시 브라우저에서 직접 눌러보고 화면·콘솔·네트워크 요청으로 확인한 뒤 결과를 보고한다.

- 각 페르소나마다 "이 사람이라면 실제로 어떻게 쓸까"를 생각하며 정상 경로뿐 아니라 실수/오조작(뒤로가기, 새로고침, 빈 값 제출, 중복 클릭 등)도 시도한다.
- 여러 명이 동시에 참여하는 실시간 기능(팀 로비, 자산 입력 동기화, 관전 등)은 브라우저 탭을 여러 개 열어 실제로 동시에 조작해 검증한다. 코드만 보고 "소켓 이벤트가 있으니 될 것이다"라고 판단하지 않는다.
- 발견한 문제는 6장 형식으로 기록하고, 세션 종료 시 8장 형식의 테스트 리포트를 `proposal/` 옆에 별도 결과 파일로 남긴다 (예: `test-reports/20260831_qa_result.md`).

## 1. 테스트 환경 준비

1. 저장소 루트에서 의존성 설치 여부 확인 후 `npm run dev` 실행 (nodemon으로 Express+Socket.io 서버가 `:3001`, Vite 개발 서버가 `:5173`에서 뜨고 `/api`, `/socket.io`는 5173 → 3001로 프록시된다).
2. Claude in Chrome으로 `http://localhost:5173` 접속. `tabs_context_mcp`로 현재 탭 상태 확인 후 새 탭 생성.
3. 배포 환경(Railway)에서 점검해야 하는 경우 사용자에게 배포 URL을 확인 요청한다 — 이 문서에는 프로덕션 도메인을 하드코딩하지 않는다.
4. 관리자 계정이 없다면 학부모/학생 테스트보다 먼저 3.3의 회원가입 절차로 테스트용 교사 계정을 하나 만들어 둔다 (예: `qa_teacher` / 임의 비밀번호). 이미 있다면 재사용한다.
5. 실시간 동기화 확인을 위해 최소 3~4개의 탭(또는 시크릿 창)을 동시에 다룰 수 있도록 준비한다 — 학생 4인 역할극 + 선생님 관전 화면을 동시에 열어야 하는 시나리오가 있다.
6. `read_console_messages`, `read_network_requests`를 시나리오 진행 중 수시로 확인해 JS 에러나 4xx/5xx 응답을 놓치지 않는다.

## 2. 세 페르소나 정의

### 2.1 학생 (플레이어)
- **목표**: 친구들과 팀을 꾸려 보드게임을 진행하고, 자기 캐릭터의 자산(직업/성공카드/부동산/주식/현금)을 입력해 게임 결과를 제출한다.
- **행동 특성**: 스마트폰으로 접속한다고 가정하고 조작한다. 코드 입력 오타, 뒤로가기 남발, 방을 잘못 나가는 등 실제 초등~중학생 사용자가 할 법한 실수를 섞는다.
- **진입 경로 (중요)**: `proposal/20260804_changed_lobby_system.md` 기준으로 게임 참여는 **교사가 만든 학급 QR을 통해서만** 가능하다. 미배정 수업 개념은 없다.
  - **(a) 학급 QR 경로 (정식)**: 교사 대시보드의 "QR 코드" → `/join?classId=…` → 이름 입력(`/join`) → 캐릭터 선택(`/select`) → **로비**(`/lobby?classId=…`, 해당 학급의 팀 그리드) → 여기서 **"방 만들기"로 새 팀 생성(호스트)** 하거나 기존 팀 카드를 눌러 합류 → 팀 화면(`/team/:code`).
  - **(b) 팀 코드 경로 (합류 전용)**: 팀장이 공유한 초대 코드/QR로 진입. 홈 "시작하기"(`/join-code`) 또는 팀 QR → 코드 입력 → 이름/캐릭터 → **이미 존재하는 그 팀으로 바로 입장**. 이 경로에는 "방 만들기"가 없다(학급 컨텍스트가 없으므로 의도된 동작).
- **핵심 화면**: (위 진입 경로) → 팀 화면(`/team/:code`) → 자산 입력(`/team/:code/individual`) → 결과/랭킹(`/result/:sessionId`, `/ranking`).

### 2.2 학부모 (경제적 잠재력 테스터)
- **목표**: "우리 아이 경제 잠재력(색깔편)" 퀴즈를 처음 보는 학부모 입장에서 끝까지 완주하고, 결과 페이지의 안내/공유 기능을 실제로 사용해본다.
- **행동 특성**: 이 앱을 처음 써보는 일반 사용자로 접근한다. 안내 문구가 이해되는지, 입력 검증이 잘 되는지(이름 공백, 나이 음수/문자 입력 등)를 함께 살펴본다.
- **핵심 화면**: 홈 → 퀴즈 소개(`/quiz`) → 퀴즈 진행(`/quiz/play`: 안내→이름→성별→나이→문항 N개) → 결과(`/quiz/result/:resultId`).

### 2.3 선생님 (관리자)
- **목표**: 여러 학급(class)을 관리하며, 각 학급 안에서 진행 중인 팀들을 실시간으로 파악하고 필요 시 개입(관전, 강퇴, 삭제, 일괄 등록)한다.
- **행동 특성**: 수업 중 여러 팀을 동시에 지켜보는 관리자 입장. 실수로 전체 삭제를 누르지 않는지 확인 다이얼로그가 실제로 막아주는지도 함께 검증한다.
- **핵심 화면**: 홈 → 관리자(톱니바퀴, `/admin`) → 로그인/회원가입 → 학급 목록 → 학급 대시보드(그리드 뷰/테이블 뷰, 검색, QR, 방 생성, 전체 삭제, 전체 등록, 관전 팝업) → 랭킹 뷰 → 설정/로그아웃.

## 3. 역할별 상세 테스트 체크리스트

### 3.1 학생 (플레이어) — 정식 플로우
1. **(경로 a)** 교사 학급 QR(`/join?classId=…`)로 진입 → 이름 입력 → 캐릭터 선택 → 로비(`/lobby?classId=…`) 진입까지 정상 라우팅 확인. 이름을 비운 채 다음으로 넘어가지지 않는지 확인.
2. **(경로 b)** 홈 "시작하기"(`/join-code`)로 진입 → 코드 없이 "팀 참여하기"가 막히는지 / 잘못된 코드(존재하지 않는 6자리)로 끝까지 진행했을 때 네이티브 `alert` 없이 앱 내부 안내(토스트)로 실패가 표시되는지 확인.
3. 로비 그리드에서 "방 만들기"로 새 방 생성 (호스트가 됨) → 팀 화면에서 초대 코드/QR이 표시되는지 확인. (경로 b에는 "방 만들기"가 없는 것이 정상 — 기존 팀에 합류만 가능)
4. 로비 그리드의 기존 팀 카드를 눌러 합류 → 팀 화면 진입 확인.
5. **[멀티탭]** 새 탭 3개를 열어 서로 다른 이름/캐릭터로 같은 초대 코드에 참여시킨다.
   - 4명이 모두 팀 화면에 실시간으로 표시되는지(소켓 `room-updated`) 각 탭에서 확인.
   - 5번째 참가 시도 시 인원 초과로 막히는지 확인.
   - 호스트 탭에서 특정 플레이어를 강퇴(kick) → 해당 탭이 자동으로 로비로 튕겨나가는지(`you-were-kicked`) 확인.
   - 호스트가 "가격 설정" 모달에서 가격을 바꾸면 다른 탭에도 즉시 반영되는지(`room-prices-updated`) 확인.
6. 임의의 한 탭에서 "자산 입력" 진입 → 직업/성공카드/부동산/주식/현금 5단계를 모두 채우고 "완료"까지 진행. 중간에 뒤로가기(이탈 확인 모달)와 StepBar 클릭으로 이전 단계 재방문이 되는지 확인.
7. 입력 도중 다른 탭에서 같은 방 화면을 보고 있을 때 실시간으로 입력 진행 상태(완료 표시)가 반영되는지 확인.
8. 호스트가 아닌 플레이어가 방을 나갈 때와, 호스트가 방을 나갈 때(방 자체가 삭제되고 나머지 인원이 `room-closed`로 로비로 이동하는지)의 차이를 각각 검증.
9. 새로고침 후 재접속(재입장, `playerUuid` 재사용)이 기존 참가자로 정상 복귀되는지, 중복 참가자로 잘못 늘어나지 않는지 확인.
10. 랭킹 페이지(`/ranking`)와 결과 페이지(`/result/:sessionId`)가 정상적으로 데이터를 보여주는지 확인.

### 3.2 학부모 (경제적 잠재력 테스터)
1. 홈에서 "우리 아이 경제 잠재력 테스트" 클릭 → 소개 화면 문구/버튼 확인.
2. "테스트 시작하기" → 안내 문구 → 아이 이름 입력(공백만 입력 시 진행 막히는지) → 성별 선택 → 나이 입력(빈 값/비숫자 처리) → 문항 진행.
3. 진행 중 상단 진행바(progress bar)가 문항 수에 맞춰 정확히 증가하는지 확인 (`data-testid="quiz-progress-fill"`).
4. 모든 문항 응답 후 "결과 분석중" → 결과 페이지로 자동 이동까지 지연 없이 되는지 확인. 네트워크 요청(`/api/quiz/results` POST)이 실패했을 때 에러 화면과 "다시 시도하기"가 동작하는지도 강제로 확인(가능하면 오프라인 시뮬레이션 또는 네트워크 요청 로그로 실패 케이스 유추).
5. 결과 페이지에서:
   - 그룹별 일러스트, 태그라인, 설명, 2개 축(오늘/내일, 안전/도전) 하이라이트가 그룹 색상에 맞게 표시되는지.
   - "우리 아이 경제 그룹 자세히 보기", "다양한 경제 유형 알아보기", "네이버 리뷰 작성하기" 링크가 새 탭으로 정상 열리는지(깨진 링크·404 없는지).
   - 공유 버튼 3종: 카카오톡 공유(카카오 SDK 미설정 시 "준비 중" 안내가 뜨는지), 링크 복사(클립보드 복사 알림 표시), 사진 다운로드(실제 이미지 파일이 받아지는지).
   - "다시 하기"로 퀴즈를 재시작할 수 있는지.
6. 존재하지 않는 `resultId`로 결과 URL에 직접 접근했을 때 에러 화면이 뜨는지 확인.

### 3.3 선생님 (관리자)
1. 홈 우측 상단 톱니바퀴 클릭 → `/admin` 진입, 아직 로그인 안 된 상태면 로그인 폼이 뜨는지 확인.
2. 회원가입 탭으로 테스트 계정 생성 → 실패 케이스(중복 아이디, 빈 값)와 성공 케이스 모두 확인. 로그인 성공 시 데스크탑형 대시보드 레이아웃(전체 화면 전환)으로 바뀌는지 확인.
3. 학급 목록 화면에서 새 학급 생성 → 목록에 반영되는지.
4. 학급 선택 → 학급 대시보드 진입:
   - 그리드 뷰: 진행 중인 팀은 참여 캐릭터 카드로, 등록 완료된 팀은 "등록 완료" 표시로 구분되는지.
   - 테이블 뷰: 플레이어별 자산 현황과 입력완료/미입력 상태 컬럼이 정확한지, 검색창으로 이름/팀 필터링이 되는지.
   - "QR 코드" 버튼으로 학급 참여용 QR/코드가 뜨는지.
   - "방 생성"으로 관리자가 직접 팀을 만들 수 있는지.
   - **[교차 검증]** 그리드 뷰의 카드를 클릭해 관전 팝업(`AdminSpectateModal`)을 열고, 3.1에서 멀티탭으로 진행 중인 실제 팀의 상태(팀원, 캐릭터, 가격, 입력 진행)가 **실시간으로 반영**되는지 확인 — 이 항목은 4장의 통합 시나리오와 함께 진행하는 것이 가장 확실하다. 참고: 이 팝업은 "읽기 전용"이 아니라 플레이어 자산 수정 / 학생 퇴장 / 가격 설정 / 결과 등록 / 팀 삭제가 가능한 **관리 패널**이다(`2026-08-06-admin-mode-room-design.md` 기준, 관리자는 방을 조회·관전·수정·삭제할 수 있다).
   - "전체 등록"(일괄 결과등록) 클릭 시 확인 다이얼로그가 뜨고, 대기 중인 팀이 없을 때/연결이 끊긴 팀원이 있을 때 각각 알맞은 안내 메시지가 뜨는지 확인.
   - "전체 삭제" 클릭 시 확인 다이얼로그 없이 바로 삭제되지 않는지, 취소 시 아무 일도 안 일어나는지 확인.
   - 개별 플레이어 삭제(테이블 뷰에서 선택 삭제)가 정상 반영되는지.
5. 랭킹 뷰 탭에서 해당 학급의 랭킹 데이터가 정확히 표시되는지 확인.
6. 설정 화면에서 로그아웃 시 다시 로그인 화면으로 돌아가고, 로그아웃 후 대시보드 관련 API를 호출하는 화면에 직접 접근 시 인증 없이 접근되지 않는지 확인.

## 4. 교차 역할 통합 시나리오 (가장 실제 사용 상황에 가까운 테스트)

한 번의 세션에서 아래 순서로 세 역할을 오가며 실시간 동기화까지 확인한다. 반드시 여러 탭을 동시에 열어두고 진행할 것.

1. **선생님 탭**: 로그인 → 새 학급 생성 → 학급 대시보드 진입 (그리드 뷰 유지, 창을 계속 열어둠).
2. **학생 탭 4개**: 해당 학급으로 각각 접속해 같은 방을 만들고 참여 (호스트 1 + 팀원 3).
3. **선생님 탭에서 실시간 확인**: 별도 새로고침 없이 그리드 뷰 카드에 방금 만든 팀이 자동으로 나타나는지(`class-rooms-updated`).
4. **선생님 탭**: 해당 팀 카드를 클릭해 관전 팝업 진입 → 학생 탭에서 캐릭터/가격 설정을 바꾸면 관전 화면에도 실시간 반영되는지 확인.
5. **학생 탭들**: 순서대로 자산 입력 5단계를 완료. 마지막 학생까지 완료하면 학생 화면은 팀 화면에 머무르고(자동 제출 없음 — 등록은 관리자 권한), 선생님 탭의 해당 팀 카드가 "등록 대기"(`completed-but-unregistered`)로 바뀌는지 확인.
5'. **선생님 탭**: 관전 팝업의 "결과 등록"(또는 대시보드 "전체 등록") → 확인 다이얼로그 → 해당 팀 전원이 `game-submitted`로 결과/랭킹 화면으로 이동하는지 확인.
6. **선생님 탭**: 그리드 뷰에 해당 팀이 "등록 완료"로 바뀌는지, 테이블 뷰에서도 전원 입력완료로 표시되는지, 랭킹 뷰에 새 결과가 반영되는지 확인.
7. 이어서 **학부모 탭**을 별도로 열어 퀴즈를 완주 — 이 결과가 학생/선생님 쪽 데이터와 섞이거나 충돌하지 않는지(완전히 독립된 기능인지) 확인.

## 5. 신규 기능 검증 절차

새 기능이 추가된 뒤 테스트를 요청할 때는 이 문서와 함께 해당 변경을 설명하는 `proposal/` 폴더의 최신 문서(들)를 같이 전달한다. Claude Code는:

1. 최신 제안서를 먼저 읽고 "무엇이 새로 생겼는지 / 무엇이 바뀌었는지"를 요약한다.
2. 관련된 역할(학생/학부모/선생님)의 2장·3장 체크리스트 중 영향받는 항목을 먼저 골라 표시하고, 새 기능이 그 항목들과 상호작용하는 지점(예: 새 화면이 기존 라우팅 흐름에 끼어드는 경우, 기존 상태값을 새로 참조하는 경우)을 짚는다.
3. 새 기능 자체를 제안서 스펙대로 동작하는지 항목별로 점검한다(스펙에 없는 임의 해석은 금지, 스펙과 다르면 "구현 누락/상이"로 별도 기록).
4. 마지막으로 새 기능과 무관해 보이는 나머지 체크리스트도 최소 1회 빠르게 훑어 회귀(regression)가 없는지 확인한다 — 특히 공용 컴포넌트(BackButton, 모달류, 소켓 이벤트 핸들러)를 건드린 변경이라면 전체 재검증을 권장한다.

## 6. 버그/이슈 리포트 형식

발견한 문제는 아래 표 형식으로 즉시 기록한다 (심각도: 치명적/높음/중간/낮음).

| 역할 | 화면/기능 | 재현 경로 | 기대 동작 | 실제 동작 | 심각도 | 비고(콘솔 에러/스크린샷 등) |
|---|---|---|---|---|---|---|
| 예: 학생 | 팀 화면 강퇴 | 호스트가 팀원 강퇴 | 강퇴된 탭이 로비로 이동하며 안내 표시 | 강퇴돼도 화면이 그대로 남음 | 높음 | 콘솔에 `you-were-kicked` 이벤트 미수신 로그 |

- 콘솔 에러(`read_console_messages`)와 실패한 네트워크 요청(`read_network_requests`)은 재현 경로와 함께 원문을 남긴다.
- 재현이 불안정한(가끔 발생하는) 이슈는 몇 번 시도 중 몇 번 발생했는지 명시한다.
- 화면 문제는 가능하면 스크린샷을, 여러 단계에 걸친 상호작용 문제는 `gif_creator`로 짧은 재현 영상을 남긴다.

## 7. Claude in Chrome 사용 가이드

- 세션 시작 시 `tabs_context_mcp`로 기존 탭 상태를 먼저 확인한다. 이 QA 목적의 새 탭은 `tabs_create_mcp`로 만들고, 사용자의 기존 탭을 재사용하지 않는다.
- 멀티플레이어 시나리오(3장 3.1-5번, 4장)는 각 "인물"마다 별도 탭을 유지하고, 어떤 탭이 어떤 역할인지 헷갈리지 않도록 탭을 만들 때마다 어떤 페르소나/캐릭터인지 기록해둔다.
- 폼 입력은 `form_input`을, 요소 클릭/스크롤 등 일반 조작은 `computer` 또는 `find` + 좌표를 활용한다.
- 화면에 보이는 텍스트를 빠르게 확인할 때는 `get_page_text`, 구조적으로 요소를 찾을 때는 `read_page`를 사용한다.
- alert/confirm 등 브라우저 네이티브 다이얼로그를 직접 트리거하지 않는다 (전체 삭제, 방 나가기 등은 앱 자체 커스텀 모달이라 문제 없지만, 브라우저 기본 `confirm()`으로 뜨는 지점이 있다면 특히 주의하고 발견 시 5장 방식으로 기록).
- 각 시나리오 진행 중간중간 `read_console_messages`로 에러를 스캔한다. 특히 소켓 재연결, `fetch` 실패 관련 로그를 놓치지 않는다.

## 8. 완료 후 산출물

세션 종료 시 아래 내용을 담은 테스트 결과 리포트를 별도 마크다운 파일로 남긴다 (예: `test-reports/YYYYMMDD_qa_result.md`, 폴더가 없다면 새로 만들어도 된다):

1. 테스트 일시, 테스트한 환경(로컬/배포), 커밋 해시 또는 최신 반영된 제안서 목록.
2. 2~3장 체크리스트 항목별 Pass/Fail/Skip 표.
3. 4장 통합 시나리오 결과 요약.
4. 발견된 이슈 전체 목록(6장 형식).
5. (신규 기능 검증 요청이었다면) 5장 절차에 따른 "스펙 대비 구현 상태" 요약.

이 리포트 파일과 이번 QA 시뮬레이션 제안서(본 문서)는 함께 보관해 다음 테스트 세션에서 회귀 여부를 비교할 수 있게 한다.
