# 머니빌리지 통합관리시스템 QA 시뮬레이션 테스트 제안서 (2026-09-10)

> 목적: 매 테스트 세션마다 이 문서 하나를 그대로 Claude Code에게 넘기면, Claude Code가 **Claude in Chrome**을 사용해 실제 브라우저에서 메인 진행자 · 은행/퀴즈/행운 관리자 · 게임 플레이어 다섯 페르소나를 직접 연기(role-play)하며 머니빌리지 통합관리시스템(`money-village`, index.html 기반 정적 SPA)의 기존 기능 정상 작동 여부와 신규 기능 구현 여부를 점검하도록 만든 재사용 가능한 QA 시나리오 문서다.
> 이 문서는 같은 저장소의 `proposal/20260831_qa_simulation_proposal.md`(머니빌리지 보드게임 어플리케이션용)와 형식을 맞춘 자매 문서이며, 대상은 **보드게임 웹앱이 아니라 진행자용 통합관리시스템**이다. 새 기능이 추가될 때마다 이 문서를 고치기보다는, `proposal/` 폴더의 최신 제안서를 함께 첨부해 "아래 시나리오 전체 + 이 신규 제안서 반영 여부"를 확인해달라고 요청하면 된다 (6장 참고).

## 0. Claude Code에게 주는 지시 요약

너는 지금부터 QA 테스터다. Claude in Chrome 브라우저 도구를 사용해 아래 다섯 페르소나를 실제로 "연기"하면서 머니빌리지 통합관리시스템(`index.html` + `js/*.js`)을 클릭·입력·확인한다. 코드를 읽고 "이러면 동작하겠네"라고 추측만 하지 말고, 반드시 브라우저에서 직접 눌러보고 화면·콘솔·네트워크 요청·Supabase 실제 반영 여부로 확인한 뒤 결과를 보고한다.

- **[최우선 원칙] 절대 기존 운영 데이터를 건드리지 않는다.** 이 시스템은 프로덕션 Supabase 프로젝트 1개만 존재하며 별도 테스트/스테이징 환경이 없다. QA는 **실제 버전 그대로**(앱 내 "테스트 모드" 토글은 사용하지 않음) 진행하되, 반드시 2장의 "식별 가능한 이름" 규칙을 지켜 QA로 생성한 데이터/게임/시민권자/업로드 파일을 실제 운영 데이터와 구분되게 만들고, 세션 종료 시 2장의 정리(cleanup) 절차를 실행해 QA 중 생성된 데이터와 결과물을 빠짐없이 삭제했는지 최종 확인한다. 이 원칙을 지키지 못했다고 판단되면 즉시 작업을 멈추고 사용자에게 보고한다.
- 각 페르소나마다 "이 사람이라면 실제로 어떻게 쓸까"를 생각하며 정상 경로뿐 아니라 실수/오조작(중복 클릭, 값 비운 채 제출, 라운드/문항 건너뛰기, 마감 후 재시도 등)도 시도한다.
- 은행/퀴즈/행운 부스는 실제 현장에서 아이패드 여러 대가 각각 `index.html`에 동시 접속해 운영된다. 브라우저 탭을 여러 개(메인 진행자 1 + 은행 1 + 퀴즈 1 + 행운 1) 동시에 열어 실제 동시 운영 상황을 재현해 검증한다. 이 앱은 보드게임 웹앱과 달리 Socket.io가 아니라 **Supabase를 3초 주기로 폴링**하는 방식으로 화면 간 동기화가 이루어지므로("실시간"이라도 즉시 반영이 아니라 최대 수 초의 지연이 있을 수 있음), 반영 여부를 확인할 때는 폴링 주기를 감안해 몇 초 대기 후 확인한다.
- 발견한 문제는 7장 형식으로 기록하고, 세션 종료 시 9장 형식의 테스트 리포트를 `proposal/` 옆에 별도 결과 파일로 남긴다 (예: `test-reports/20260910_qa_result_management_system.md`).

## 1. 테스트 환경 준비

이 앱은 빌드 스텝이 없는 순수 정적 SPA다(`index.html` + `<style>` 내장 CSS + `js/` 개별 스크립트). React 라우터나 Express/Socket.io 서버가 없으므로 보드게임 제안서의 `npm run dev`류 절차는 적용되지 않는다.

1. 저장소 루트(`money-village/`)에서 로컬 정적 서버를 실행한다 (예: `npx serve .` 또는 `python -m http.server`). `file://index.html`로 직접 여는 방식은 지양한다 — 일부 fetch/모듈 동작이 파일 프로토콜에서 달라질 수 있고, 아이패드 여러 대가 네트워크로 동시 접속하는 실제 운영 환경과 더 가깝게 재현하기 위해서다.
2. Claude in Chrome으로 로컬 서버 주소(`http://localhost:PORT`)에 접속. `tabs_context_mcp`로 현재 탭 상태 확인 후, 페르소나 수만큼 새 탭을 생성한다.
3. 이 앱은 브라우저 경로(URL)로 화면을 구분하지 않고 `switchScreen(id)`로 화면을 전환하는 단일 페이지 구조다. 즉 특정 화면으로 바로 이동하는 딥링크가 없으므로, 각 탭마다 홈 화면부터 실제 버튼 클릭으로 원하는 화면(설정/계수/보고서/명예의전당/은행/퀴즈/행운 등)까지 이동해야 한다. 탭을 새로 만들 때마다 "이 탭은 어떤 페르소나/부스인지"를 기록해 헷갈리지 않도록 한다.
4. `adminScreen`(퀴즈 정답 이미지 관리)은 SHA-256 비밀번호 인증이 필요하다. 이 화면은 5개 페르소나의 필수 기능 목록에는 포함되어 있지 않으므로 이번 QA 범위에서는 제외하되, 우연히 진입 경로가 노출되는지 정도만 가볍게 확인한다.
5. 이 앱은 Supabase에 직접 연결되어 있고 배포 환경이 별도로 없다(정적 파일을 그대로 서빙). 배포 URL(예: Vercel/정적 호스팅)이 있어 그 환경에서 점검해야 하는 경우 사용자에게 URL을 확인 요청한다 — 이 문서에는 도메인을 하드코딩하지 않는다.
6. Web Serial API(Arduino) 연동(`js/arduino.js`)은 실물 하드웨어가 필요하므로 이번 QA 범위에서 제외한다. 관련 버튼이 실물 기기 없이 클릭됐을 때 앱이 죽지 않고 적절히 실패 처리되는지 정도만 가볍게 확인한다.
7. `read_console_messages`, `read_network_requests`를 시나리오 진행 중 수시로 확인해 JS 에러나 Supabase 4xx/5xx 응답을 놓치지 않는다.

## 2. 테스트 데이터 정리 원칙 (반드시 준수)

이 시스템은 별도 스테이징 환경 없이 **프로덕션 Supabase 1개**만 사용한다. **이번 QA는 앱의 "테스트 모드" 토글(`#btnTestModeO`, `isSampleMode`/`is_test`)을 사용하지 않고, 실제 버전 그대로 진행한다.** 즉 QA 중 만드는 게임은 명예의 전당·과거 게임 목록·시민권자 목록에 실제 운영 데이터와 똑같이(자동 구분 태그 없이) 나타난다. 그만큼 "식별 가능한 이름으로 만들기"와 "끝나면 확실히 지우기"가 유일한 방어선이 되므로, 아래 절차를 빠짐없이 지킨다.

### 2.1 식별 가능한 이름 사용 (시작 전 필수)

테스트 모드 태그가 없으므로, 사람이 봐도 즉시 QA 데이터임을 알 수 있도록 처음부터 이름으로 구분해 둔다.

- 게임을 식별하는 분반/날짜 등 입력값에는 `QA테스트` 등 눈에 띄는 식별자를 포함한다 (예: 분반명에 `QA테스트`).
- QA 중 새로 등록하는 시민권자의 실명/닉네임에는 `QA_` 접두어를 사용한다 — 실제 시민권자 마스터 목록(`users`, `is_citizen:true`)에 그대로 섞여 들어가므로 더욱 중요하다.
- 게임을 시작하자마자 생성된 `game_id`를 바로 기록해 둔다(2.2 정리용). "테스트 모드"처럼 나중에 자동으로 구분해주는 장치가 없으므로, 진행 중 어느 화면에서든 게임/분반을 다시 선택해야 할 때는 이름을 재확인하고 실제 운영 게임을 잘못 건드리지 않도록 각별히 주의한다.

### 2.2 세션 종료 후 정리(Cleanup) — 필수

QA 세션을 마치기 전, 1단계에서 기록한 `game_id`를 가지고 아래를 실행한다.

1. `sbDeleteGame(gameId)`를 호출한다. 이 함수는 `bank_history, bank_state, quiz_history, quiz_state, cash_balance, stock_balance, stock_price, estate_balance, estate_price, traits, success_factors, game_individual, game_team, game_info` 테이블에서 해당 `game_id`의 데이터를 일괄 삭제한다.
2. **주의: 위 삭제 목록에 `luck_history`/`luck_state`가 빠져 있다** (행운 기능이 추가된 이후 이 함수가 갱신되지 않은 것으로 추정됨). 따라서 행운 부스를 테스트했다면 `sbDeleteLuckHistory(gameId)`를 **별도로 반드시 호출**해야 한다. 이 문제 자체를 7장 형식의 이슈로도 기록한다(정리 누락은 실제 버그이기도 하다).
3. QA 중 새로 등록한 시민권자(2.1의 `QA_` 접두어 대상)는 모두 `sbDeleteCitizen(nickname)`으로 삭제한다. 이번에는 실제 등록(`is_citizen:true`)이므로 이 단계를 빠뜨리면 시민권자 마스터 목록에 QA 데이터가 영구히 남는다.
4. **Google Drive에 업로드된 PDF도 함께 정리 대상이다.** 테스트 모드를 쓰지 않으므로 "자산리포트 PDF 출력/드라이브 저장", "명예의 전당 PDF 출력/드라이브 저장"을 실제로 클릭하면 GAS(`uploadPDF`)를 통해 실제 `ASSET_FOLDER_ID`/`HALL_FOLDER_ID` Drive 폴더에 파일이 그대로 업로드된다. `CLAUDE.md` 기준 GAS(`gas/Code.js`)에는 `uploadPDF`/`listTestReports`만 있고 **파일 삭제 액션이 없어 이 문서의 자동화(Claude in Chrome)만으로는 Drive 파일을 지울 수 없다.** 따라서:
   - PDF 파일명에 QA 식별자가 남도록(2.1에서 정한 `QA_`/`QA테스트` 이름이 자연스럽게 파일명에 들어가는지 확인) 진행하고,
   - 업로드된 정확한 파일명·업로드 시각·대상 폴더(자산리포트 vs 명예의 전당)를 9장 리포트에 목록으로 남겨,
   - **세션 종료 후 사용자가 Google Drive에서 직접 확인·삭제**할 수 있도록 안내한다. Claude Code가 임의로 Drive 파일을 지우려 시도하지 않는다(권한·API가 없을 뿐 아니라 잘못 지우면 실제 운영 파일을 건드릴 위험이 있다).
5. 정리가 끝나면 명예의 전당·시민권자 목록·과거 게임 불러오기 목록에서 QA 흔적(이름으로 식별)이 남아있지 않은지 최종적으로 화면에서 눈으로 재확인한다.
6. 9장의 최종 리포트에 "생성했던 QA 게임 `game_id` / Supabase 정리 완료 여부 / Drive에 남아있어 수동 삭제가 필요한 파일 목록"을 반드시 기록한다.

### 2.3 알려진 한계 (사용자 확인 필요)

- `sbDeleteGame`이 `luck_*` 테이블을 커버하지 못하는 점 외에도, 삭제 함수 목록이 스키마 변경 속도를 못 따라갈 가능성이 있다. 정리 후에는 반드시 화면상 재확인(2.2-5)까지 수행해 이런 누락을 QA 스스로 이중 점검한다.
- Drive에 업로드된 PDF는 이 QA 절차로 자동 삭제되지 않는다(2.2-4). 완전한 정리를 위해서는 QA 세션 종료 후 사용자가 Drive에서 수동으로 지워야 한다는 점을 리포트에 명확히 알린다.

## 3. 다섯 페르소나 정의

### 3.1 메인 진행자
- **목표**: 행사 전 게임을 준비(시민권자/명단 등록)하고, 행사 중·후에 참가자 자산을 입력해 최종 결과와 개인별 리포트를 산출한다.
- **행동 특성**: 준비 단계와 현장 진행 단계, 그리고 행사 후 재확인/수정 단계를 오간다. 입력 실수(빈 값, 중복 닉네임), 게임 도중 화면 전환, 잘못된 과거 게임을 불러오는 실수를 함께 점검한다.
- **핵심 화면**: `setupScreen`(게임설정/시민권자 관리/명단입력) → `countingScreen`(자산 입력) → `reportScreen`(결과/자산리포트/PDF·드라이브 저장/게임 불러오기) → `fameScreen`(명예의 전당) → `reportHubScreen`/`testReportScreen`/`eftiReportScreen`(경제적 잠재력·유형 보고서).

### 3.2 은행 관리자
- **목표**: 예금 부스(`bankScreen`)를 운영하며 이자율·라운드를 설정하고, 진행 중 신청 현황을 모니터링하다 마감한다.
- **행동 특성**: 행사 시작과 동시에 부스를 켜두고 계속 지켜본다. 마감 전/후 동작 차이, 데이터 초기화의 파급 범위를 신중히 확인한다.
- **핵심 화면**: `bankScreen`.

### 3.3 퀴즈 관리자
- **목표**: 퀴즈 부스(`quizScreen`)를 운영하며 보상을 설정하고, 진행 현황을 모니터링하다 마감한다.
- **행동 특성**: 은행 관리자와 유사하나 퀴즈 문항/정오답 흐름이 추가된다.
- **핵심 화면**: `quizScreen`.

### 3.4 행운 관리자
- **목표**: 행운 부스(`luckScreen`)를 운영하며 가위바위보/룰렛/주사위 3종 게임의 보상 배수를 설정하고, 진행 현황을 모니터링하다 마감한다.
- **행동 특성**: 은행/퀴즈보다 애니메이션·연출이 많은 화면이라 렌더링/타이밍 이슈가 발생하기 쉽다. 마감·초기화 시 **브라우저 네이티브 `confirm()`/`alert()`**가 뜨는 것이 확인되었으므로(예: "행운 게임을 마감합니다... 마감하시겠습니까?"), 8장의 다이얼로그 처리 가이드를 반드시 따른다.
- **핵심 화면**: `luckScreen`.

### 3.5 게임 플레이어
- **목표**: 은행/퀴즈/행운 부스 키오스크 화면에서 자신의 캐릭터(개인 또는 팀)로 예금 신청, 퀴즈 풀이, 행운 게임 참여를 하고 결과를 확인한다.
- **행동 특성**: 이 시스템에는 플레이어 전용 로그인이나 별도 화면이 없다 — 부스 관리자가 켜둔 **공용 키오스크 화면**(아이패드 한 대를 여러 참가자가 돌아가며 사용)에서, 참가자별 버튼을 눌러 본인 차례에 조작하는 방식이다. 따라서 게임 플레이어 페르소나는 별도 탭이 아니라 **부스 탭 안에서** 여러 참가자 역할을 순서대로(때로는 빠르게 연속으로) 연기하며 검증한다.
- **핵심 화면**: `bankScreen`/`quizScreen`/`luckScreen` 내 참가자용 조작 영역(참가자 버튼 → 신청/풀이/배팅 화면).

## 4. 역할별 상세 테스트 체크리스트

> 아래 체크리스트는 기능 단위의 "무엇을 확인해야 하는가"를 정의한 것이며, 정확한 버튼 위치·문구는 Claude Code가 실제 화면에서 확인한다(추측 금지). 진행 전 관련 스크립트(`js/setup.js`, `js/counting.js`, `js/report.js`, `js/bank.js`, `js/quiz.js`, `js/luck.js`)를 먼저 훑어 대략적인 함수/상태 흐름을 파악한 뒤 브라우저에서 검증하면 더 정확하다.

### 4.1 메인 진행자
1. **게임설정**: 홈에서 설정 화면 진입 → 게임 변형(`basic`/`advanced`/`rich_vessel`) 선택 시 화면 구성(주식 6종 vs 부동산 6종, `traits` vs `successFactors`)이 올바르게 바뀌는지 확인.
2. **주식/부동산 가격설정**: 초기 가격 입력·수정이 실제 게임 진행/리포트 계산에 반영되는지 확인.
3. **명단입력 / 시민권자 관리**: 개인/팀 모드 전환, 참가자 행 추가/삭제, 닉네임 중복 검증(중복 시 알림 후 진행 차단)을 확인. 시민권자 DB 탭에서 등록·수정·삭제(모달 폼/인라인 폼 양쪽)를 확인.
4. **시민권자 불러오기**: 명단 입력 행에서 기존 시민권자를 검색해 실명/닉네임/EFTI가 자동 채워지는지, 일치하는 대상이 없을 때 적절한 안내가 뜨는지 확인.
5. **[필수] 식별 가능한 이름으로 실제 게임 시작**: 테스트 모드 토글은 켜지 않고(2장 참고), 분반명 등에 `QA테스트` 식별자를 포함해 게임을 시작 → 이후 화면(예: "이전 편집" 버튼 노출 등)이 정상적으로 전환되는지 확인. 생성된 `game_id`를 바로 기록해 둔다(2.2 정리용).
6. **자산 입력**: `countingScreen`에서 참가자별 현금(권종), 성실활동금, 주식/부동산 보유량, 플레이 스타일(`traits`, basic) 또는 경제적 성공요소(`successFactors`, advanced/rich_vessel)를 입력하고 다음 참가자로 넘어가는 흐름을 확인. 값을 비운 채 넘어갈 때의 동작, 이전 참가자로 되돌아가 값을 고치는 동작을 확인.
7. **결과 발표**: 전원 입력 완료 후 종료 처리 → 순위(`rankIndiv`/`rankTeam`/`teamTotal`) 재계산이 정확한지, 팀 모드에서 팀 합산이 올바른지 확인.
8. **자산리포트 결과 확인**: `reportScreen`에서 참가자별 리포트 전환(이전/다음), 개인 자산 상세가 입력값과 일치하는지 확인.
9. **자산리포트 PDF 출력 / 드라이브 저장**: PDF 생성이 실제로 되는지(입력 필드가 표시용 `<span>`으로 정상 치환되는지 포함) 확인하고, "드라이브 저장"까지 실제로 실행해 GAS `uploadPDF` 요청이 성공(200)하는지 `read_network_requests`로 확인한다. **이 버튼은 실제로 Google Drive에 파일을 업로드하므로**, 업로드된 파일명·시각을 즉시 메모해 둔다(2.2-4 정리용).
10. **게임 불러오기**: `reportScreen`의 과거 게임 목록에서 **QA로 직접 만든(이름으로 식별 가능한)** 게임을 정확히 찾아 선택 → 날짜/분반/변형이 올바르게 로드되는지, 존재하지 않거나 손상된 게임을 불러올 때 에러 처리가 되는지 확인. 테스트 모드 태그가 없어 목록상 실제 운영 게임과 구분되지 않으므로, **분반/날짜 이름을 두 번 확인한 뒤 클릭**한다.
11. **자산 수정**: 불러온 게임의 특정 참가자 자산을 수정 후 재저장 → 순위/리포트에 즉시 반영되는지, 수정이 다른 참가자 데이터를 건드리지 않는지 확인.
12. **명예의 전당 확인**: `fameScreen`에서 역대 순위가 게임 변형별로 올바르게 표시되는지 확인. 테스트 모드를 쓰지 않았으므로 **방금 만든 QA 게임도 정상적으로 명예의 전당에 노출되는 것이 맞는 동작**이다 — 이 노출은 2.2 정리(`sbDeleteGame`) 완료 후 사라지는지까지 확인해야 검증이 끝난다(즉 "노출되지 않아야 함"이 아니라 "정리 후에는 사라져야 함"이 이번 체크포인트다).
13. **명예의 전당 출력/PDF/드라이브 저장**: 위 자산리포트와 동일한 관점으로 확인.
14. **경제적 잠재력 테스트 보고서 / 경제적 유형 보고서 출력**: `testReportScreen`(Smore 설문 결과 JSONP 조회)과 `eftiReportScreen`(이름/나이/EFTI/날짜 직접 입력 → 즉시 출력)이 각각 정상 동작하는지, 입력값 검증(빈 값/이상값)이 되는지 확인. 이 두 기능은 참가자 게임 데이터와 무관하게 독립적으로 동작하므로, 2장의 테스트 데이터 정리 대상에 해당하지 않는지(즉 정말 게임 데이터와 분리되어 있는지)도 함께 확인한다.

### 4.2 은행 관리자
1. **이자배율설정**: 초기 설정 화면에서 라운드별 예금 유형(장기/중기/단기)과 이자율을 설정 → 저장이 `localStorage`(`mv_bank_settings`)와 Supabase(`bank_state`) 양쪽에 반영되는지 확인.
2. **라운드 관리**: 3라운드 전환이 올바른 순서로 진행되는지, 라운드를 건너뛰거나 되돌릴 때의 동작을 확인.
3. **은행진행현황 확인**: 참가자별 예금 신청 상태가 화면에 표시되는지, 4.5의 플레이어 조작 이후 (3초 폴링을 감안해) 몇 초 내로 반영되는지 확인.
4. **데이터 초기화**: 초기화 시 확인 다이얼로그(브라우저 네이티브일 가능성이 높음 — 8장 참고)가 뜨는지, 초기화 후 신청 내역이 실제로 비워지는지 확인. **QA로 만든 게임의 `game_id`에서만 초기화되고 다른(특히 실제 운영) 게임에 영향이 없는지** 반드시 확인 — 실수로 다른 게임을 초기화하면 되돌릴 수 없다.
5. **마감**: 마감 후 신규 신청이 차단되는지, 마감 버튼 상태(텍스트/비활성화)가 바뀌는지, 마감 후 재시도 시 적절한 안내가 뜨는지 확인.

### 4.3 퀴즈 관리자
1. **보상설정**: 초기 설정에서 보상 값을 설정 → `quiz_state`에 반영되는지 확인.
2. **퀴즈진행현황 확인**: 참가자별 풀이 상태(정답/오답/미응시)가 표시되는지, 폴링 지연을 감안해 반영 여부를 확인.
3. **데이터 초기화**: 4.2-4와 동일한 관점(다이얼로그, 다른 게임에 영향 없는지, 실제 초기화 여부).
4. **마감**: 4.2-5와 동일한 관점.

### 4.4 행운 관리자
1. **보상설정**: 초기 설정에서 가위바위보(기본 4배)/룰렛(기본 5배)/주사위(기본 7배) 배수를 설정 → `luck_state`(`luck_history`/`luck_state` 테이블)에 반영되는지 확인. 기본값이 실제로 저 배수와 일치하는지도 확인.
2. **행운진행현황 확인**: 참가자별 참여 이력(`luck_history`: `game_id`, `user_id`, `amount`, `matured_amount`, `luck_type`)이 화면에 표시되는지 확인.
3. **데이터 초기화**: "이전에 기록되었던 모든 데이터가 삭제됩니다" 확인 문구가 뜨는 **네이티브 `confirm()`**을 8장 가이드에 따라 처리하고, 실제 삭제 여부·다른 게임에 영향이 없는지를 확인.
4. **마감**: "행운 게임을 마감합니다. 이후 진행이 불가능합니다. 마감하시겠습니까?" **네이티브 `confirm()`**을 8장 가이드에 따라 처리하고, 마감 후 버튼이 "마감됨"으로 바뀌며 비활성화되는지, 마감 후 플레이어 조작이 실제로 막히는지 확인.

### 4.5 게임 플레이어 (은행/퀴즈/행운 부스 공용 화면에서 검증)
1. **(은행) 팀/개인 예금 신청**: 참가자 버튼 클릭 → 예금 신청서 화면에서 금액 설정 후 신청 → 신청 내역이 즉시(또는 폴링 주기 내) 반영되는지 확인. 개인 모드/팀 모드 각각 확인.
2. **(은행) 신청내역 삭제**: 본인이 신청한 내역을 삭제할 수 있는지, 삭제 후 다시 신청할 수 있는지 확인.
3. **(은행) 라운드별 상태 확인**: 라운드가 넘어갈 때 이전 라운드 신청 내역과 현재 라운드 신청 가능 여부가 참가자 화면에 올바르게 구분되어 보이는지 확인.
4. **(퀴즈) 팀/개인 퀴즈 풀이**: 문항 진행, 정답/오답 처리, 이미 푼 문항 재응시 가능 여부를 확인.
5. **(퀴즈) 풀이 현황 확인**: 본인의 정오답 현황을 참가자 화면에서 확인할 수 있는지 확인.
6. **(행운) 가위바위보/룰렛/주사위 진행**: 참가자 버튼 → 게임 선택 → 배팅 금액 설정(예금 신청서 화면과 동일한 UI로 안내됨 — 실제로 동일한지 비교 확인) → 배팅 완료 → 각 게임(가위바위보 3버튼, 룰렛 4색, 주사위 멈춤 버튼)이 애니메이션 정지 후 승패를 올바르게 판정하는지 확인. 참가 횟수 제한이나 쿨다운이 없다는 스펙(설계 문서 기준)대로 연속 참여가 실제로 가능한지도 확인.
7. **(행운) 베팅 결과 확인**: 승/패/무 각각에서 보상 지급 여부(이겼을 때만 지급, 비기거나 졌을 때는 미지급)가 정확한지, 결과 화면 안내 문구가 맞는지 확인.

## 5. 교차 역할 통합 시나리오 (실제 행사 흐름 재현)

사용자가 설명한 실제 운영 흐름을 그대로, **실제 버전으로**(테스트 모드 미사용) 재현한다. 반드시 여러 탭을 동시에 열어두고 진행하며, 2.1의 이름 식별 규칙을 철저히 지킨다.

1. **메인 진행자 탭**: 시민권자 등록/불러오기 → 명단 입력 → 분반명에 `QA테스트` 식별자를 포함해 게임 시작(사전 준비 단계 재현). 생성된 `game_id`를 바로 기록한다.
2. **은행/퀴즈/행운 탭 3개**: 각각 부스 화면 진입 → 초기 설정(이자율/보상/배수) → 부스 오픈 상태로 대기(현장 부스 동시 운영 재현). 세 탭 모두 1단계와 **동일한 `game_id`/분반**을 대상으로 하고 있는지 다시 확인한다.
3. **은행/퀴즈/행운 탭에서 참가자 역할 연기**: 각 부스 공용 화면에서 2~3명의 가상 참가자로 예금 신청/퀴즈 풀이/행운 게임을 각각 진행한다.
4. **메인 진행자 탭에서 실시간 확인**: 은행/퀴즈/행운 관리자 화면의 "진행현황"에 방금 참가자 조작이 반영되는지, 폴링 지연(최대 수 초)을 감안해 확인한다.
5. **메인 진행자 탭**: **게임 불러오기**로 1단계에서 만든(이름으로 식별한) 게임을 정확히 찾아 다시 불러온 뒤, `countingScreen`으로 진입해 각 참가자의 현금/성실활동금/주식(또는 부동산)/플레이 스타일(또는 성공요소)을 입력한다(현장 진행 중 결정된 자산을 사후 입력하는 실제 흐름 재현). 목록에 실제 운영 게임과 함께 섞여 보이므로 분반/날짜를 한 번 더 확인한다.
6. **은행/퀴즈/행운 탭**: 각각 **마감**을 실행한다(네이티브 confirm 처리는 8장 가이드 준수). 마감 후 해당 부스에서 신규 참여가 막히는지 재확인한다.
7. **메인 진행자 탭**: 전원 자산 입력 완료 후 **결과 발표** → 순위 재계산 → `reportScreen`에서 개인별 리포트 확인. 이때 은행/퀴즈/행운에서 발생한 보상(`depositReward`/`questReward`, 행운 보상)이 최종 자산에 정확히 합산되는지 확인 — 이 지점이 여러 부스와 메인 진행자 데이터가 실제로 합쳐지는 가장 중요한 교차 검증 포인트다.
8. **메인 진행자 탭**: 자산리포트 PDF 출력·드라이브 저장, 명예의 전당 PDF 출력·드라이브 저장까지 실제로 실행하고, 업로드된 파일명/시각을 메모한다(2.2-4). 명예의 전당에서 방금 만든 QA 게임이 정상적으로 노출되는지 확인한다(테스트 모드를 쓰지 않았으므로 노출되는 것이 정상 — 9단계 정리 후 사라지는지가 검증 포인트).
9. **정리**: 2.2 절차대로 `sbDeleteGame` + `sbDeleteLuckHistory`(+ `sbDeleteCitizen`)를 실행하고, 명예의 전당/시민권자 목록/과거 게임 목록에서 Supabase 데이터 흔적이 없는지 최종 확인한다. 8단계에서 업로드된 Drive 파일 목록을 정리해 리포트에 남기고, 실제 삭제는 사용자에게 안내한다(자동 삭제 불가, 2.2-4 참고).

## 6. 신규 기능 검증 절차

새 기능이 추가된 뒤 테스트를 요청할 때는 이 문서와 함께 해당 변경을 설명하는 `proposal/` 폴더의 최신 문서(들)를 같이 전달한다. Claude Code는:

1. 최신 제안서를 먼저 읽고 "무엇이 새로 생겼는지 / 무엇이 바뀌었는지"를 요약한다.
2. 관련된 역할(3장의 다섯 페르소나)의 4장 체크리스트 중 영향받는 항목을 먼저 골라 표시하고, 새 기능이 그 항목들과 상호작용하는 지점(예: 새 화면이 기존 `switchScreen` 흐름에 끼어드는 경우, 기존 전역 상태 `players[]`/`isSampleMode` 등을 새로 참조하는 경우)을 짚는다.
3. 새 기능 자체를 제안서 스펙대로 동작하는지 항목별로 점검한다(스펙에 없는 임의 해석은 금지, 스펙과 다르면 "구현 누락/상이"로 별도 기록).
4. 새 기능이 2장의 정리(cleanup) 대상(`sbDeleteGame` 등 삭제 함수, Drive 업로드)을 새로 건드리는 기능이라면(예: 새 테이블 추가, 새로운 GAS 업로드 액션), **삭제 함수 목록에 그 테이블이 포함되었는지, 새 업로드가 생겼다면 그것도 2.2-4 Drive 정리 대상에 추가해야 하는지 반드시 확인**한다 — 행운 기능 추가 때 `sbDeleteGame`이 갱신되지 않았던 사례(2.2 참고)가 재발하지 않도록 하는 것이 이 문서의 핵심 취지 중 하나다.
5. 마지막으로 새 기능과 무관해 보이는 나머지 체크리스트도 최소 1회 빠르게 훑어 회귀(regression)가 없는지 확인한다 — 특히 공용 로직(`recalculateAllRankings`, `switchScreen`, Supabase 삭제/초기화 함수)을 건드린 변경이라면 전체 재검증을 권장한다.

## 7. 버그/이슈 리포트 형식

발견한 문제는 아래 표 형식으로 즉시 기록한다 (심각도: 치명적/높음/중간/낮음).

| 역할 | 화면/기능 | 재현 경로 | 기대 동작 | 실제 동작 | 심각도 | 비고(콘솔 에러/스크린샷 등) |
|---|---|---|---|---|---|---|
| 예: 행운 관리자 | 데이터 초기화 | `sbDeleteGame` 실행 후 명예의 전당 확인 | QA 게임의 행운 기록도 함께 삭제되어야 함 | `luck_history`가 삭제되지 않고 남음 | 높음 | `sbDeleteGame` 삭제 테이블 목록에 `luck_history`/`luck_state` 누락 (2.2 참고) |

- 콘솔 에러(`read_console_messages`)와 실패한 네트워크 요청(`read_network_requests`)은 재현 경로와 함께 원문을 남긴다.
- 재현이 불안정한(가끔 발생하는, 특히 3초 폴링 타이밍에 의존하는) 이슈는 몇 번 시도 중 몇 번 발생했는지 명시한다.
- 화면 문제는 가능하면 스크린샷을, 애니메이션이 관여하는 행운 게임 등 여러 단계에 걸친 상호작용 문제는 `gif_creator`로 짧은 재현 영상을 남긴다.
- **테스트 데이터 정리와 관련된 문제(2장)는 심각도를 한 단계 격상해 기록**한다 — 운영 데이터 오염으로 이어질 수 있는 항목이기 때문이다.

## 8. Claude in Chrome 사용 가이드

- 세션 시작 시 `tabs_context_mcp`로 기존 탭 상태를 먼저 확인한다. 이 QA 목적의 새 탭은 `tabs_create_mcp`로 만들고, 사용자의 기존 탭을 재사용하지 않는다.
- 다중 부스 시나리오(4장 4.2~4.5, 5장)는 각 "역할/부스"마다 별도 탭을 유지하고, 탭을 만들 때마다 어떤 페르소나/부스인지 기록해둔다.
- **[중요] 이 앱은 브라우저 네이티브 `confirm()`/`alert()`를 실제로 사용한다** (예: 행운 부스의 마감/초기화, 이전 게임 불러오기 실패 시 `alert`). Claude in Chrome은 네이티브 다이얼로그를 트리거하면 이후 명령을 받지 못하게 되므로, 이런 동작을 유발하는 버튼을 누르기 **직전에** `javascript_tool`로 `window.confirm`/`window.alert`를 임시로 오버라이드해 자동으로 승인/확인 처리되도록 만든 뒤 클릭한다(예: `window.confirm = () => true; window.alert = (m) => { console.log('[QA-ALERT]', m); };`). 오버라이드 사실과 원래 표시됐어야 할 문구는 `console.log`로 남겨 `read_console_messages`로 확인·기록한다. 이렇게 하지 않고 실수로 실제 네이티브 다이얼로그를 띄웠다면, 세션이 멈췄을 가능성이 높으므로 사용자에게 수동으로 다이얼로그를 닫아달라고 안내한다.
- 폼 입력은 `form_input`을, 요소 클릭/스크롤 등 일반 조작은 `computer` 또는 `find` + 좌표를 활용한다.
- 화면에 보이는 텍스트를 빠르게 확인할 때는 `get_page_text`, 구조적으로 요소를 찾을 때는 `read_page`를 사용한다.
- 은행/퀴즈/행운 화면의 진행현황이 갱신되는지 확인할 때는 클릭 직후 바로 판단하지 말고, 3초 폴링 주기를 감안해 약간 대기한 뒤 재확인한다(즉시 반영되지 않았다고 바로 버그로 단정하지 않는다).
- 각 시나리오 진행 중간중간 `read_console_messages`로 에러를 스캔한다. 특히 Supabase 요청 실패, `sbInitGame`/`sbDeleteGame` 계열 함수의 에러 로그를 놓치지 않는다.

## 9. 완료 후 산출물

세션 종료 시 아래 내용을 담은 테스트 결과 리포트를 별도 마크다운 파일로 남긴다 (예: `test-reports/YYYYMMDD_qa_result_management_system.md`, 폴더가 없다면 새로 만들어도 된다):

1. 테스트 일시, 테스트한 환경(로컬 정적 서버/배포), 사용한 게임 변형(`basic`/`advanced`/`rich_vessel`) 목록, 최신 반영된 제안서 목록.
2. **생성했던 QA 게임의 `game_id` 목록, 2.2 Supabase 정리 절차 수행 여부·결과(성공/일부 누락 등), 그리고 자동 삭제되지 않아 사용자가 Drive에서 직접 지워야 하는 업로드 파일 목록(파일명/업로드 시각/폴더)** — 이 항목은 다른 항목보다 먼저, 눈에 띄게 기록한다.
3. 4장 체크리스트 항목별(페르소나 5개 기준) Pass/Fail/Skip 표.
4. 5장 통합 시나리오 결과 요약(특히 7단계 "부스 보상이 최종 자산에 합산되는지" 결과를 명시).
5. 발견된 이슈 전체 목록(7장 형식).
6. (신규 기능 검증 요청이었다면) 6장 절차에 따른 "스펙 대비 구현 상태" 요약.

이 리포트 파일과 이번 QA 시뮬레이션 제안서(본 문서)는 함께 보관해 다음 테스트 세션에서 회귀 여부를 비교할 수 있게 한다.
